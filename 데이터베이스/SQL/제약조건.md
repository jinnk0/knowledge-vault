제약조건(Constraint)은 잘못된 값의 입력·수정을 DBMS가 거부하게 만드는 규칙으로, 데이터의 무결성을 지키기 위해 테이블에 정의한다. 보통 [[데이터베이스/SQL/DDL.md|DDL]]로 테이블을 만들거나 변경할 때 함께 지정한다.

## 종류

대표적인 무결성 제약은 PRIMARY KEY, FOREIGN KEY, UNIQUE, NOT NULL, CHECK다. DEFAULT는 제약이 아니라 값을 생략했을 때 넣을 기본값을 정하는 절이지만, 함께 정의하는 경우가 많아 같이 정리한다.

| 구분 | 하는 일 | NULL |
|---|---|---|
| PRIMARY KEY | 행을 유일하게 식별한다 (유일성 + NOT NULL) | 불가 |
| FOREIGN KEY | 부모 테이블의 PK/UNIQUE 값을 참조한다 (참조 무결성) | 컬럼이 허용하면 가능 |
| UNIQUE | 값의 중복을 금지한다 | DBMS별 차이 |
| NOT NULL | NULL을 금지한다 | 불가 |
| CHECK | 조건식이 FALSE인 값을 거부한다 | Oracle에서는 UNKNOWN 통과 |
| DEFAULT | 값을 생략하면 기본값을 넣는다 | 제약이 아니라 기본값 절 |

```sql
CREATE TABLE 부서 (
  부서번호 INT PRIMARY KEY,      -- 유일 + NOT NULL
  부서명 VARCHAR(30) UNIQUE      -- 중복 금지, Oracle에서는 NULL 허용
);

CREATE TABLE 사원 (
  사원번호 INT PRIMARY KEY,
  부서번호 INT,
  급여 INT CHECK (급여 > 0),
  재직여부 CHAR(1) DEFAULT 'Y',
  CONSTRAINT fk_부서 FOREIGN KEY (부서번호)
    REFERENCES 부서(부서번호) ON DELETE CASCADE   -- 부모 삭제 시 자식도 삭제
);
```

- **PRIMARY KEY**: 유일성과 NOT NULL을 동시에 강제하므로, NULL도 중복도 넣을 수 없다. 여러 컬럼을 묶은 복합키는 가능하지만, 기본키 제약 자체는 테이블당 하나다. 개념적인 정의는 [[데이터베이스/데이터 모델링/키.md|키]] 노트에서 다룬다.
- **UNIQUE**: 중복은 막지만 항상 NOT NULL인 것은 아니다. Oracle의 고유키는 NULL을 허용하며, NULL 처리 방식은 DBMS마다 다르다. 예를 들어 SQL Server의 UNIQUE 제약은 NULL을 하나만 허용한다. (출처: Microsoft Learn) NULL까지 막으려면 NOT NULL을 함께 지정한다.
- **CHECK**: Oracle의 CHECK는 조건이 FALSE면 거부하지만, [[데이터베이스/NULL.md|NULL]]이 끼어 UNKNOWN이 되면 통과시킨다. 그래서 `CHECK (COL > 0)`에 NULL을 넣으면 입력이 성공하며, NULL을 막으려면 NOT NULL도 지정해야 한다. 반대로 AND 조건에서 한쪽이 FALSE면 다른 쪽이 UNKNOWN이어도 전체가 FALSE이므로 거부된다.
- **DEFAULT**: 컬럼을 생략했을 때 기본값을 채운다. 명시적으로 NULL을 넣으면 DEFAULT는 적용되지 않는다.

```sql
INSERT INTO 사원 (사원번호, 부서번호, 급여) VALUES (1, 10, NULL);  -- CHECK 통과 (UNKNOWN)
INSERT INTO 사원 (사원번호, 부서번호, 급여) VALUES (2, 10, -5);    -- CHECK 위반 (FALSE)
INSERT INTO 사원 (사원번호, 부서번호, 급여, 재직여부)
VALUES (3, 10, 100, NULL);                                         -- 재직여부는 'Y'가 아니라 NULL
```

## 무결성의 종류

제약조건이 지키는 무결성은 세 종류로 나눈다.

| 무결성 | 지키는 대상 | 관련 제약 |
|---|---|---|
| 개체 무결성 | 기본키의 유일성과 NOT NULL | PRIMARY KEY |
| 참조 무결성 | 외래키가 실재하는 부모 값을 가리키는지 | FOREIGN KEY |
| 도메인 무결성 | 컬럼 값이 허용된 범위·형식인지 | CHECK, 데이터 타입 |

기본키 값이 중복되어 생기는 오류는 참조 무결성이 아니라 개체 무결성 위반이다. 참조 무결성은 외래키에 관한 이야기다.

## 외래키와 참조 무결성

외래키(FK)는 자식 테이블에 정의하고, 부모 테이블의 기본키 또는 고유키를 가리킨다. 참조 방향은 자식 → 부모다.

자식의 FK는 부모의 PK에 실재하는 값만 가질 수 있다. 자식의 FK 값을 부모에 없는 값으로 INSERT·UPDATE하면 참조 무결성 위반으로 실패한다. 즉 부모에 'A'가 있어야 자식이 'A'를 참조할 수 있다. 단, FK 컬럼이 NULL을 허용하면 NULL은 위반이 아니다.

부모 행을 삭제할 때 그 행을 참조하는 자식 행을 어떻게 처리할지는 FK에 지정한 옵션에 따라 달라진다. 다음 두 테이블에서 부서 10을 삭제하는 경우를 보자.

| 부서 (부모) 부서번호 |
|---|
| 10 |
| 20 |

| 사원 (자식) 사원번호 | 사원 (자식) 부서번호 (FK) |
|---|---|
| 101 | 10 |
| 102 | 10 |

| 옵션 | 부서 10을 삭제하면 |
|---|---|
| `ON DELETE CASCADE` | 부서 10을 참조하던 사원 101, 102도 함께 삭제된다 |
| `ON DELETE SET NULL` | 사원 101, 102의 부서번호가 NULL로 바뀐다 (NULL을 허용하는 FK여야 한다) |
| 옵션 생략 (Oracle) | 참조하는 자식이 있으므로 부서 10의 삭제가 거부된다 (RESTRICT처럼 동작) |

DML 관점의 삭제 동작은 [[데이터베이스/SQL/DML.md|DML]] 노트에서도 다룬다.

## 제약 위반과 트랜잭션

즉시 검사하는 제약을 하나의 DML 문장이 위반하면 그 문장만 실패한다. 같은 트랜잭션에서 앞서 정상 수행된 문장까지 자동으로 취소되지는 않는다. 반면 지연(Deferred) 제약은 트랜잭션 종료 시점에 검사될 수 있다. 트랜잭션의 확정과 취소는 [[데이터베이스/SQL/TCL.md|TCL]] 노트에서 다룬다.
