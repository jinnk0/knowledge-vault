[[클린 코드/코드 품질/코드 품질.md|코드 품질]]의 핵심 요소 중 예측 가능성과, 오용하기 어려운 코드를 작성해야 한다는 원칙을 실현하는 방법이다. 다른 개발자와 협업하는 환경에서 코드를 예측 가능하고 오용하기 어렵게 만들려면, 코드의 중요한 세부 사항을 다른 개발자에게 전달하는 여러 기법이 필요한데, 이를 코드 사이의 계약으로 다루는 것이 코드 계약이다.

## 코드는 혼자 존재하지 않는다

추상화 계층으로 잘 분리한 코드는 하위 문제의 해결책으로 다른 곳에서도 얼마든지 재사용될 수 있다. 그런데 요구 사항은 계속 변하고, 자신이 작성한 코드가 독립적으로 존재하는 경우는 거의 없다. 다른 개발자가 작성한 코드에 의존하게 되고, 다른 개발자도 자신의 코드에 의존하는 코드를 작성하게 된다.

다른 개발자들이 활발하게 코드를 변경하더라도 코드 품질이 유지되려면 코드가 튼튼하고 사용하기 쉬워야 한다. 그러려면 다른 개발자가 코드를 변경하거나 코드와 상호작용할 때 어떤 문제가 발생할 수 있는지, 발생한다면 어떻게 완화할 수 있을지를 미리 이해하고 선제적으로 조치해야 한다. 이때 특히 고려해야 하는 것이 다음 세 가지다.

### 자신에게 분명하다고 해서 다른 사람에게도 분명한 것은 아니다

어떤 문제를 해결할 때는 충분한 고민과 사고를 거쳐 코드를 작성하기 때문에, 정작 작성한 사람은 그 코드를 분명하게 읽을 수 있지만 다른 사람에게는 그렇지 않다. 그래서 코드가 어떻게 사용되어야 하는지, 무엇을 하는지, 왜 그 일을 하는지를 항상 설명해야 한다. 이것이 주석문을 많이 작성해야 한다는 뜻은 아니다. 코드 자체를 이해하기 쉽게 만들어 코드 스스로 설명이 되게 하는 것이 더 좋은 방법이다.

### 다른 개발자는 무의식중에 여러분의 코드를 망가뜨릴 수 있다

작성한 코드는 다른 코드로부터 전혀 영향을 받지 않는 독립적인 존재가 아니라, 끊임없이 변화하는 코드 위에 놓여 있고, 그 위에도 계속해서 변화하는 코드가 쌓인다. 다른 사람들은 그 코드가 왜 존재하는지, 무슨 일을 하는지에 대한 사전 지식이 없을 수 있어서, 의도치 않게 잘 실행되던 코드를 작동하지 않게 만들거나 오용하는 방식으로 코드를 추가·수정할 가능성이 크다. 다른 개발자의 변경으로 자신의 코드가 작동하지 않거나 오용되는 결과가 생긴다면, 그 변경은 문제가 해결되기 전까지 코드베이스에 병합되어서는 안 된다. 그러려면 문제가 있을 때 코드 컴파일이 중지되거나 테스트가 실패하도록 만들어야 한다.

### 시간이 지나면 자신의 코드도 기억하지 못한다

1~2년 전에 작성한 코드를 다시 들여다보는 일은 다른 사람이 작성한 코드를 보는 것과 크게 다르지 않다. 배경지식이 거의 없거나 전혀 없는 사람에게도 자신의 코드가 이해하기 쉬워야 하고, 잘 작동하던 코드에 버그가 발생하기는 어려워야 한다.

## 다른 개발자는 코드 사용법을 어떻게 아는가

다른 개발자가 여러분의 코드를 사용하거나 여러분의 코드에 의존하는 코드를 수정할 때, 그들은 여러 가지 상황에서 어떤 [[클린 코드/추상화 계층/함수.md|함수]]를 호출해야 하는지, [[클린 코드/추상화 계층/클래스.md|클래스]]가 무엇을 나타내고 언제 사용되어야 하는지, 어떤 값을 인수로 써야 하는지, 코드가 수행하는 동작이 무엇인지, 어떤 값을 반환하는지를 파악해야 한다.

이를 알아내기 위해 다른 개발자가 할 수 있는 일은 다음과 같다.

- 함수, 클래스, 열거형 등의 이름을 살펴본다.
- 함수와 생성자의 매개변수 유형, 반환값의 유형 같은 데이터 유형을 살펴본다.
- 함수·클래스 수준의 문서나 주석문을 읽어본다.
- 직접 와서 묻거나 채팅·이메일로 문의한다.
- 함수와 클래스의 자세한 구현 코드를 읽는다.

이 중 처음 세 가지(이름 확인, 데이터 유형 확인, 문서 읽기)만이 실제로 사용할 만하고, 그중에서도 이름과 데이터 유형을 확인하는 것이 문서를 읽는 것보다 더 신뢰할 만하다.

### 이름 확인

이름을 확인하는 것은 개발자들이 새로운 코드의 사용법을 알아내기 위해 실제로 가장 많이 쓰는 방법 중 하나다. 패키지, 클래스, 함수의 이름은 책의 목차와 같아서, 하위 문제를 해결할 코드를 찾는 편리하고 빠른 방법이 된다. 자신의 코드를 다른 개발자가 어떻게 사용해야 하는지 가장 잘 전달할 수 있는 방법 중 하나도 이름을 잘 짓는 것이다.

### 데이터 유형 확인

유형 시스템을 갖춘 언어로 코드를 작성하는 것은 다른 개발자가 코드를 오용하거나 오작동시킬 수 없도록 막는 좋은 방법 중 하나다.

### 문서 읽기

코드 사용법에 관한 문서는 함수·클래스 수준의 비공식적인 주석문, 자바독(JavaDoc) 같은 좀 더 공식적인 코드 내 문서, README나 웹 페이지 같은 외부 문서 등 여러 형태로 존재할 수 있다. 다만 문서 읽기는 신뢰도가 높지 않고, 코드 사용법을 알리는 방법으로도 적절하지 않다.

- 다른 개발자가 이 문서들을 읽는다는 보장이 없고, 실제로 읽지 않을 때가 많다.
- 읽더라도 잘못 해석할 수 있다. 다른 개발자에게 익숙하지 않은 용어를 썼을 수도 있고, 코드가 해결하려는 문제에 대해 다른 개발자가 가진 지식 수준을 잘못 가정하고 문서를 썼을 수도 있다.
- 문서의 업데이트가 제대로 되지 않을 수 있다. 코드를 변경할 때마다 문서도 업데이트해야 하는데, 이를 잊으면 문서 내용이 더 이상 유효하지 않게 된다.

### 직접 물어보기

코드를 작성한 지 얼마 안 됐다면 효과적일 수 있다. 하지만 그 코드를 작성한 사람과 연락할 방법이 없거나 작성한 지 오래됐다면 신뢰하기 어려운 방법이다.

### 코드를 살펴보는 것

코드 사용법에 대한 가장 확실한 답은 구현 세부 사항을 직접 살펴보는 것에서 얻을 수 있다. 하지만 이 방법은 실용적이지 않고, 코드의 양이 많으면 효과를 얻기 힘들다. [[클린 코드/추상화 계층/추상화 계층.md|추상화 계층]]을 만드는 요점은 개발자가 한 번에 몇 가지 개념만 처리하면 되고, 하위 문제가 정확히 어떻게 해결되었는지 몰라도 그 해결책을 쓸 수 있어야 한다는 데 있다. 코드 사용법을 알기 위해 구현 세부 사항을 읽어야 한다면, 이는 추상화 계층이 주는 이점을 스스로 부정하는 셈이 된다.

## 코드 계약이란

계약에 의한 프로그래밍(programming by contract) 또는 계약에 의한 디자인(design by contract)은, 다른 사람이 코드를 어떻게 사용할지 그리고 코드가 무엇을 할 것으로 기대할 수 있는지를 코드 간의 상호작용을 계약처럼 여기고 다루는 것이다. 어떤 코드를 호출하는 쪽은 특정 요건을 충족해야 하고, 호출되는 코드는 원하는 값을 반환하거나 일부 상태를 수정한다. 모든 것이 이 계약에서 정의되기 때문에 분명하지 않은 부분이 없고, 예상과 다르게 실행되는 일도 없다.

코드 계약에 대한 용어는 다음 세 가지 범주로 나누면 유용하다.

- **선결 조건(precondition)**: 코드를 호출하기 전에 사실이어야 하는 것. 시스템이 어떤 상태에 있어야 하는지, 코드에 어떤 입력을 공급해야 하는지와 같은 사항이다.
- **사후 조건(postcondition)**: 코드가 호출된 후에 사실이어야 하는 것. 시스템이 새로운 상태에 놓인다든지, 반환되는 값과 같은 사항이다.
- **불변 사항(invariant)**: 코드가 호출되기 전과 후에 시스템 상태를 비교했을 때 변경되지 않아야 하는 사항이다.

코드를 작성할 때는 이렇게 만들어지는 계약의 내용이 무엇일지, 그리고 어떻게 하면 코드를 사용하는 사람이 그 계약을 파악하고 따라갈 수 있을지 생각하는 것이 중요하다.

## 계약의 명확한 부분과 세부 조항

코드에서 계약을 정의할 때는 명확한 부분과 세부 조항이 함께 있다.

- **명확한 부분**: 함수와 클래스 이름, 인자 유형, 반환 유형, 검사 예외(checked exception)
- **세부 조항**: 주석문과 문서, 비검사 예외(unchecked exception)

코드 계약에서는 조건을 명확한 부분으로 드러내는 것이 세부 조항에 의존하는 것보다 훨씬 낫다. 사람들이 세부 조항을 읽지 않는 경우가 많고, 세부 조항은 업데이트가 제때 되지 않기 때문이다. 세부 조항에 너무 많이 의존하면 오용하기 쉬운 취약한 코드가 되고, 예상과 다르게 동작하기도 쉬워진다. 물론 세부 조항을 완전히 피할 수 없는 경우도 있는데, 이때는 문서화를 명확히 해야 한다. 다만 이것이 이상적인 방법은 아니므로, 명확하게 만들 방법이 있다면 그 방법을 쓰는 것이 좋다.

### 세부 조항을 제거하는 방법

다른 개발자가 코드를 올바르게 사용하게 하려면, 세부 조항에 의존하기보다는 잘못된 사용 자체를 처음부터 불가능하게 만드는 편이 낫다. 코드 계약의 세부 조항에 있는 항목을, 발생 자체가 불가능하거나 적어도 실수할 가능성이 없는 명백한 항목으로 바꿀 수 있는 경우가 있다. 코드가 오용되거나 잘못 설정되면 컴파일조차 되지 않도록 하는 것이 목표다.

예를 들어 정적 팩토리 클래스를 사용하면, 어떤 상태(state)나 가변성(mutability)이 클래스 외부로 노출되는 것을 없앨 수 있다.

- **상태**: 객체가 담고 있는 어떤 값이나 데이터
- **가변적(mutable)**: 객체를 만든 후에도 그 상태를 수정할 수 있는 경우
- **불변적(immutable)**: 객체를 생성한 후에는 상태를 변경할 수 없는 경우

## 세부 조항을 확인하는 방법: 체크와 어서션

컴파일러로 코드 계약을 확인하는 것에 대한 대안으로 런타임 검사를 쓸 수 있다. 이 방법은 일반적으로 컴파일 타임 확인만큼 강력하지 않은데, 계약 위반의 발견이 코드를 실행하는 동안 발생하는 문제에 대한 테스트(또는 사용자)에 의존하기 때문이다. 반면 컴파일 타임 확인은 계약 위반 자체를 논리적으로 불가능하게 만든다. 그럼에도 컴파일러로 계약을 강제할 실질적인 방법이 없는 상황이 있는데, 이런 경우에는 런타임 검사로 계약을 확인하는 것이 아예 확인하지 않는 것보다 낫다.

| 구분 | 컴파일러 방식 (정적 검사) | 런타임 방식 (동적 검사) |
|---|---|---|
| 핵심 메커니즘 | 수학적·논리적 명제 증명 (제어 흐름 분석, 심볼릭 실행, SMT 솔버) | 조건식 실행 및 평가 (가드 구문, 어서션, AOP 코드 주입) |
| 확인 시점 | 빌드·컴파일 타임 (실행 전) | 런타임 (실제 코드가 실행되는 순간) |
| 검증 대상 | 모든 가능한 실행 경로 (100%의 경우의 수) | 실제 입력되어 실행된 특정 경로 |
| 책임 주체 | 컴파일러·정적 분석 도구 | 실행 엔진·프로그램 자체 |
| 계약 위반 시 동작 | 빌드 실패(컴파일 에러)로 실행 파일 생성 자체를 거부 | 예외 발생·프로그램 종료 (`ContractException`, `AssertionError` 등) |
| 사전 조건 검증 방식 | 호출자(caller) 검증: 함수를 부르는 지점에서 위반 가능성이 있으면 컴파일 거부 | 피호출자(callee) 진입 시 검증: 함수 입구에서 입력값을 조건문으로 평가 |
| 사후 조건 검증 방식 | 피호출자 구현 검증: 함수 내부 로직이 약속된 반환값을 보장하는지 추론 | 함수 탈출 시 검증: `return` 직전에 반환값이 조건에 맞는지 평가 |
| 성능 영향 | 없음 (실행 속도·메모리에 영향 없음) | 있음 (조건 평가 로직으로 인한 오버헤드 발생) |
| 주요 한계점 | 파일·네트워크 I/O, 사용자 입력 등 외부 불확실성 데이터는 정적 증명 불가 | 조건문 위치에 실제 도달하지 않으면 숨은 계약 위반 버그를 놓칠 수 있음 |

### 체크

코드 계약 조건을 확인하는 일반적인 방법은 체크(check)를 사용하는 것이다. 체크는 코드 계약이 준수되었는지(입력 매개변수에 대한 제약 조건이나 수행해야 할 설정에 대한 제약 등) 확인하기 위한 추가 로직이며, 준수되지 않을 경우 명백해서 놓치고 넘어갈 수 없는 오류(또는 이와 유사한 실패)를 일으킨다.

체크는 시행 중인 계약 조건에 따라 다음과 같이 나뉜다.

- **전제 조건 검사**: 입력 인수가 올바른지, 초기화가 수행되었는지, 일부 코드를 실행하기 전에 시스템이 유효한 상태인지 확인한다.
- **사후 상태 검사**: 반환값이 올바른지, 일부 코드를 실행한 후 시스템이 유효한 상태인지 확인한다.

체크는 버그가 아무도 모르게 발생하는 것을 막아 세부 조항이 많았던 원래 코드를 개선하지만, 오용을 아예 불가능하게 만드는 해결책만큼 이상적이지는 않다. 체크를 사용할 때 기대하는 것은, 코드가 오용되면 고객에게 배포되거나 실제 프로덕션에서 서비스되기 전에 개발 단계나 [[클린 코드/코드 품질/테스트.md|테스트]] 단계에서 발견되고 수정되는 것이다. 그러나 체크의 효과가 항상 보장되지는 않는다.

- 테스트하기 불분명한 상황에서만 위반이 발생하는 조건이라면, 코드가 배포되고 사용자가 사용하기 전까지 버그가 드러나지 않을 수 있다.
- 체크가 잘 작동하더라도, 프로그램이 멈추지 않고 예외가 로그로만 기록되면 그 로그를 신경 쓰지 않는 한 발견되지 않을 위험이 있다.

코드 계약에서 세부 조항을 피할 수 없다면 계약 준수 여부를 확인하는 체크를 추가하는 것이 좋다. 다만 가능하다면 처음부터 세부 조항 자체를 피하는 것이 더 바람직하다.

체크를 함께 사용하면 좋은 테스트 기법으로 퍼즈 테스트(fuzz test)가 있다. 퍼즈 테스트는 코드나 소프트웨어의 버그, 잘못된 설정을 드러낼 수 있는 입력값을 생성해 수행하는 테스트의 한 종류로, 체크와 함께 쓰면 잘못된 설정이나 버그를 발견할 가능성을 높이는 데 도움이 된다.

### 어서션

어서션(assertion)은 코드 계약을 준수하도록 강제하는 방법이라는 점에서 체크와 매우 비슷하다. 어서션과 체크의 주요 차이점은, 배포를 위해 빌드할 때 어서션은 보통 컴파일에서 제외된다는 점이다. 성능을 향상하고 코드 오류 발생률을 낮추기 위해서다.

다만 배포용 빌드에도 어서션을 포함할 방법은 있다. 이 경우 어서션은 체크와 다르지 않고, 다만 어떤 종류의 오류나 예외를 일으킬 수 있는지에 대한 세부 사항이 조금 다를 뿐이다.
